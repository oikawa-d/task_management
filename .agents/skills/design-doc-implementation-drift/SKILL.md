# 設計書と実装の乖離

## 事象

PR全件レビューで、設計書の記述と実装が食い違っている箇所が7件見つかった。いずれも設計書側の更新も行われていなかった。

| 設計書の規定 | 実装 | 該当文書 |
|---|---|---|
| フォームは React Hook Form + zod | 手書きの検証関数（依存すら未追加） | `basic_design/05_frontend.md:13` |
| 状態管理は TanStack Query | 独自singletonストア（Pub-Sub） | `screen/08_task_detail_modal.md` §4/§5/§9 |
| 生年月日はプルダウン×3（年/月/日） | `<input type="date">` | `screen/09_settings.md` UI要素表 |
| タブ切替時はパネル先頭の見出しへフォーカス | タブボタン間の移動のみ | `screen/09_settings.md` §13 |
| props名 `onCardClick` | `onTaskClick` | `screen/07_project_board.md` §8 |
| `authStore` は `accessToken` を保持 | `TokenStore` 内部のみに保持 | `basic_design/05_frontend.md:257` |
| 実装パスは `features/board/...` | `features/task-detail/...`（issue記載と設計書が不一致） | `screen/08_task_detail_modal.md` |

### 指摘を修正する過程で新たな逸脱を作った

レビュー指摘を修正した2つのPRで、いずれも**別の規約違反が新たに持ち込まれた**。

- 「CSRFヘッダを付与せよ」の修正で、`createAuthAdapter("session")` を既定値としてハードコードした（`AUTH_MODE` は本来 `/auth/config` から実行時取得する設計）
- 「上限値をハードコードするな」の修正で、**設計書に記載のない環境変数を2つ新規追加**した（設計書の環境変数一覧への追記は伴わなかった）

## 原因

- 実装時に設計書の該当節を読まず、issue本文だけを見て着手していた
- 設計書と異なる方式を選ぶ判断をしたとき、その判断を設計書へ反映するか記録するかをしていなかった
- 「規約Aを守る」ための修正が「規約Bを破る」ことに気づかないまま完了扱いにしていた
- 実装が先行して環境変数・型・パスを増やし、文書側が追従しなかった

## 正しい対処

### 実装前

- issue本文だけで着手せず、**設計書の該当節を必ず読む**。特に確認すべきもの:
  - 技術選定（ライブラリ、状態管理、フォーム、HTTPクライアント）
  - UI要素表（入力形式、選択肢の持ち方）
  - アクセシビリティ要件（フォーカス管理、ARIA属性）
  - 環境変数一覧、型・レスポンス契約、実装ファイルパス
- 設計書とissueの記載が食い違っている場合は**補完せず確認する**。どちらかを直してから着手する

### 設計書と異なる方式を選ぶとき

設計書からの逸脱は「実装を合わせる」か「設計書を更新する」の**どちらかを必ず選び、選んだ理由を記録する**。黙って実装だけ進めない。

- 実装のほうが妥当な場合 → 同一PR内で設計書を更新する
- 判断が phase を跨ぐ場合 → issueを起票して方針決定を明示し、PR本文に既知の差分として記載する

### 環境変数・型・パスを追加するとき

- 新規の環境変数を追加したら、**必ず `.env.example` と設計書の環境変数一覧の両方に追記する**
- 既定値には設計書に記載された値を使い、根拠（どの文書のどの記述か）をコメントで残す
- `.env` 本体は勝手に読み取り・変更しない（新規項目の追加のみ許可）

### レビュー指摘を修正するとき

修正が完了したと判断する前に、**入れた変更が他の規約に触れていないか**を確認する。

- [ ] 値をハードコードしていないか（configまたは環境変数へ外部化したか）
- [ ] 追加した環境変数・型・パスを設計書へ反映したか
- [ ] 暫定対応をした場合、その制約（何が未解決か）を報告に明記したか
- [ ] 指摘の一部だけを直して「完了」と報告していないか
