# API契約と型・モックの乖離

## 事象

フロントエンドの型定義が、設計書のAPIレスポンス契約と一致していなかった。

`frontend/src/features/board/types.ts` の `BoardTask` と、`docs/detailed_design/api/tasks/01_get_project_tasks.md` の `TaskSummary` 契約の突合結果:

| フィールド | 設計書 `TaskSummary` | 実装 `BoardTask` |
|---|---|---|
| `is_active` | **必須（null不可）** | **欠落** |
| `created_by` | 契約に存在しない | **`UserSummary`（必須）** |
| `project_id` | 契約に存在しない | `string \| null` |

**この不整合が型チェックもテストもすり抜けた**。テストのモックタスクに `created_by` の値を手で書いていたため、型エラーにもテスト失敗にもならなかった。

実害:

1. `created_by` は実レスポンスに存在しないため**実行時 `undefined`**。`created_by.display_name` に触れた時点でクラッシュする
2. `is_active` の欠落により、設計書が規定する `include_inactive=true` 時の論理削除タスク表示が実装できない

## 原因

- 型定義を設計書のレスポンス契約と突合せず、実装者の想像で書いた
- モックデータを型定義に合わせて作ったため、**型が間違っていてもモックが型を満たしてしまい**、テストが常にパスした
- テストが「型定義どおりに動くか」を検証しており、「実APIレスポンスで動くか」を検証していなかった

## 正しい対処

### 型定義を書くとき

- レスポンス型は**設計書のレスポンス項目表と1対1で突合してから書く**。フィールド名・必須/任意・null許容・型をすべて照合する
- 契約に無いフィールドを型に追加しない。UI都合で必要なら、レスポンス型とは別の派生型（`type BoardTaskView = TaskSummary & { ... }`）として明示的に分離する
- 契約にあるフィールドを省略しない。使っていなくても定義する

  ```bash
  # 突合対象の契約を探す
  grep -rn "<型名>\|<エンドポイント>" docs/detailed_design/api/
  ```

### モックデータを作るとき

- モックは**設計書のレスポンス例をそのまま使う**。型定義に合わせて手で組み立てない
- 型定義とモックの両方を実装者が書くと、**両者が同じ誤解を共有して検証が無効化される**。設計書という第三の情報源に必ず当たる
- 実レスポンスに存在しないフィールドをモックに足していないか、追加した各フィールドについて契約を確認する

### 検証

- 型・モック・設計書の三者が一致しているかを、PR前に1度突合する
- 要検討: レスポンス契約からの型・モック自動生成（OpenAPIスキーマ等）の導入。実装済みでないため、現状は手動突合が必要
